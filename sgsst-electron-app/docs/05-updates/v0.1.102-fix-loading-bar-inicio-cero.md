# v0.1.102 - Fix: Barra de carga inicia en 0% y se anima de forma continua

**Fecha:** 17 de junio de 2026
**Versión:** 0.1.102
**Tipo:** Fix / Mejora UX
**Módulo afectado:** Autenticación (Login) — Pantalla de carga / Overlay de transición

---

## Resumen Ejecutivo

La pantalla de carga mostrada al iniciar sesión (overlay con logo K+, mensajes dinámicos y barra de progreso) padecía dos problemas visuales:

1. **La barra aparecía ya avanzada** (≈50%) en lugar de iniciar en 0%.
2. **La animación se sentía "saltarina"** — parecía que la carga se ejecutaba dos veces, con la barra reiniciándose a la mitad de la transición.

Ambos síntomas tenían la misma causa raíz: una regla CSS en conflicto que controlaba el ancho de la barra con una animación propia, anulando el control por JavaScript.

---

## Cambios Detallados

### 1. `styles.css` — Regla CSS en conflicto eliminada

**Antes** (líneas 1351-1363, regla duplicada con animación CSS):

```css
/* PROBLEMA: Animación CSS independiente que anula el JS */
.progress-fill {
  width: 50%;
  animation: progressAnimation 2s infinite;
}

@keyframes progressAnimation {
  0% { width: 0%; }
  50% { width: 50%; }
  100% { width: 100%; }
}
```

**Después:** regla eliminada por completo. La barra de progreso del overlay ahora se controla únicamente desde JavaScript con `requestAnimationFrame`.

**Por qué era el problema:**

- La regla tenía `width: 50%` como valor base.
- La animación `progressAnimation` corría por su cuenta, independientemente de lo que JavaScript escribiera en `style.width`.
- Cuando el overlay aparecía, la animación ya estaba en un punto intermedio (50% o más), por eso la barra se veía ya avanzada al primer frame.
- JavaScript escribía un nuevo valor, pero la animación CSS "ganaba" porque se aplicaba con mayor especificidad y se reescribía cada frame.

### 2. `renderer.js` — `animateToProgress` con estado continuo

**Antes:** la barra se animaba con `setInterval` + `CSS transition`, lo que provocaba un "salto" si se llamaba varias veces en la misma fase.

**Después:** `animateToProgress(from, to, duration, onComplete)` usa `requestAnimationFrame` y guarda `this.progress = endVal` al finalizar, de modo que la siguiente llamada **continúa desde el valor actual** en lugar de reiniciar desde 0.

```javascript
async animateToProgress(toPercent, duration = 400) {
  const startVal = this.progress;        // ← continúa desde el valor actual
  const endVal = Math.max(0, Math.min(100, toPercent));
  const startTs = performance.now();

  return new Promise(resolve => {
    const step = (now) => {
      const t = Math.min(1, (now - startTs) / duration);
      const eased = 1 - Math.pow(1 - t, 3);   // easeOutCubic
      const value = startVal + (endVal - startVal) * eased;
      this.progressBar.style.width = `${value}%`;
      this.progressText.textContent = `${Math.round(value)}%`;

      if (t < 1) {
        requestAnimationFrame(step);
      } else {
        this.progress = endVal;               // ← guarda estado para próxima llamada
        resolve();
      }
    };
    requestAnimationFrame(step);
  });
}
```

### 3. `renderer.js` — `executeLoginTransition` con secuencia sincronizada

La transición de login ahora tiene una sola secuencia de carga continua, sin re-inicios visibles:

| Fase | Mensaje | % barra | Duración |
|------|---------|---------|----------|
| 1 | "Verificando credenciales…" | 0% → 25% | ~600ms |
| 2 | "Cargando configuración…" | 25% → 55% | ~500ms |
| 3 | "Preparando interfaz…" | 55% → 80% | ~500ms |
| 4 | "Completando…" | 80% → 100% | ~400ms |
| 5 | "¡Bienvenido, [usuario]!" + check SVG | 100% (mantiene) | ~1200ms |
| 6 | Fade-out del overlay | — | ~400ms |

**Antes:** la barra se reiniciaba a 0% en cada fase (visual de "doble carga").
**Después:** la barra avanza continuo de 0 a 100% con el texto y el porcentaje siempre sincronizados.

### 4. `renderer.js` — `button.disabled` en el submit del login

Para eliminar la posibilidad de que se enviara el formulario dos veces (clicks rápidos, doble Enter, etc.) cuando el usuario hacía clic en "Ingresar":

```javascript
form.addEventListener('submit', async (e) => {
  e.preventDefault();
  const submitButton = form.querySelector('button[type="submit"]');
  if (submitButton) submitButton.disabled = true;
  try {
    // ... validación y authLoginV1 ...
    await executeLoginTransition(userName);
    // ...
  } finally {
    if (submitButton) submitButton.disabled = false;
  }
});
```

### 5. `renderer.js` — `logBuffer` con evasión FIFO y caché del elemento

Correcciones de fondo (memory + perf) que se aprovecharon en esta misma sesión:

- `logBuffer` ahora hace *eviction* cuando supera 500 entradas (antes crecía sin tope, fuga de memoria).
- `logTextarea` se cachea en una variable en lugar de hacer `getElementById` en cada log (ahorro de queries DOM).

## Lecciones Aprendidas

- **CSS animations vs JS control de la misma propiedad**: nunca mezclar. Si JS controla `width` (o `transform`, `opacity`, etc.), el CSS no debe tener una animación sobre esa misma propiedad o se producirá un "tira y afloja" donde solo gana la última regla aplicada.
- **Especificidad y orden de aplicación**: aunque JS escribe `style.width` inline, una animación CSS en una clase con animación aplicada al mismo elemento la reescribirá cada frame. El `!important` en JS tampoco gana contra una animación en ejecución.
- **Estado continuo en animaciones**: en cualquier `animateTo(a, b)` se debe guardar `currentValue = b` al terminar; si no, la siguiente llamada piensa que todavía estamos en `a` y la transición "salta".
- **Protección contra double-submit**: cualquier formulario async debe poner `button.disabled = true` antes de la llamada y restaurar en `finally`. Es la forma más simple y confiable.

## Explicación Simple

### El problema
Al abrir la app y poner las credenciales, salía una pantalla bonita de carga con una barra de progreso. Pero la barra aparecía ya por la mitad en lugar de empezar en cero, y daba la sensación de que la carga se repetía dos veces.

### La causa
En las hojas de estilo del sistema había una regla vieja que ponía la barra a la mitad desde el primer momento y la animaba sola con su propio reloj. Esa regla "ganaba" contra el código que intentaba controlarla, así que la barra mostraba lo que la regla vieja quería, no lo que el sistema necesitaba en cada momento.

### La solución
Se eliminó esa regla vieja para que solo el sistema controle la barra de un solo lugar, y se ajustó la forma en que se mueve para que recuerde en qué punto va y continúe desde ahí, en lugar de volver a empezar. También se bloqueó el botón de "Ingresar" después del primer clic para que no se procese la misma contraseña dos veces si el usuario hace doble clic rápido.

### Antes vs Después
**ANTES (con bug):** La barra aparecía a la mitad desde el inicio. Se veía que la carga se reiniciaba y daba sensación de que el sistema "se trababa y volvía a empezar".

**DESPUÉS (corregido):** La barra arranca en 0% y avanza parejo hasta 100%, con el porcentaje y los mensajes siempre coincidiendo. Se siente una sola carga fluida de principio a fin.
